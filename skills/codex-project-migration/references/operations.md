# Windows 迁移执行与接续手册

本页命令是给 Codex 的调用约定。执行时把大写占位符替换成经过核对的绝对路径，作为独立参数传递。给操作者的 PowerShell 命令使用单引号并将路径内的单引号写成两个单引号。普通检查从项目树外启动；**唯一例外是步骤 6 的旧聊天探针，必须继承该聊天的默认工作目录**。帮助命令和测试使用 `python -B`，Python 版本至少 3.12。

## 运行目录与恢复

`OLD` 为原实体目录，`NEW` 为目标，`BACKUP` 为 OLD 的同级目录“原名_迁移备份”。`RUN` 在两盘项目与备份之外，默认选择目标父目录下私有的 `.migration-checks/项目名-日期时间-短随机码`。先检查审计父目录的访问权限，使其适合保存本机文件路径和聊天标识。给用户说明该目录的用途，并在退出 Codex 前发给用户其绝对路径。Skill 安装位置须能在改名期间持续访问。

| 何时 | 调用（脚本均在 Skill 的 scripts 目录） |
|---|---|
| 核对项目身份后 | `run_record.py start OLD NEW --project-id ID --run RUN`，专用审计父目录预先创建 |
| 每步完成/停下 | `run_record.py mark --run RUN --step N --status passed/waiting/blocked/not_applicable --evidence "结果和证据路径" --next-action "谁来做什么"`，状态选其一；仅在步骤 6 确认从未存在适用旧聊天时使用 not_applicable |
| 重新打开后 | `run_record.py show --run RUN`，验证相应实体、报告和当前桌面配置后从真实阶段恢复 |

检查点按顺序追加。旧记录说明当时的观察；重新开始时仍须核实现状。如实际已完成而检查点中断在此前，验证并补登该步，不重复改名、发送消息或修复。若已通过的步骤发生变化，用 `run_record.py reopen --run RUN --step N --evidence "发现的变化" --next-action "修复和复核步骤"` 使该步及其后各步回到待核验状态，原证据保留。修复后重新逐步核验。旧运行目录与本次不同的情况不得混用。确需用全新候选替代有冲突的副本时，保留旧运行证据，为新候选建立新运行及所有权记录。不得编辑 owner.json 或切换计划以强行认可新目录。

## 1–3 · 保全与复制

1. 检查物理源根、目标父目录和可用空间，识别已有/嵌套/重定向目标、被占用文件、任何独立工作树、硬链接和重解析点。源/目标/备份/审计不得相互包含。列出会写入的任务与已打开文档；用户暂停写入，Codex 不终止进程。核对是否为项目主仓或非 Git 目录；若选到某个独立工作树，应先核实主仓与用户意图。记录桌面项目和聊天基准（见聊天手册）。主目录中若另有嵌套 Git 仓库、子模块或引用外置 Git 数据的 `.git` 文件，逐个核实。普通非 Git 根目录的基准不会覆盖其中独立仓库；需要另行采集或设计路径修复时停在该步。
2. 运行 `git_check.py baseline OLD --out RUN/git-before.json` 后，通过 `tree_copy.py copy OLD NEW --audit RUN/tree-copy` 创建可核验的完整副本。非 Git 项目保留“不适用”结论。检查进程退出码、报告和差异数；不能只凭复制工具显示成功。仅对经证实为本次创建且身份仍匹配的目标使用恢复功能。
3. 再运行 `tree_copy.py verify OLD NEW --audit RUN/tree-copy`。检查文件/目录数、每条相对路径、全部文件与命名流 SHA-256、内部硬链接成员、属性/时间、适用的有效访问规则，以及源读取前后稳定性。清单和错误留在 RUN。哈希一致不自动等于权限一致。子级重解析点、跨项目硬链接或无法保真的特殊结构要说明具体类型和影响；目前支持普通本地 NTFS 文件、目录、树内硬链接、命名数据流、有效 DACL/owner/group。压缩、加密、稀疏、云占位或依赖树外对象等特殊情形停止并保留原件，说明缺口。SACL 审计策略不在助手的核验范围内。
4. 如果源发生写入，保存并暂停相关任务，重新读取基准。若只读校验已发现本次候选中的差异，保留源和候选，识别哪一侧发生变化。可安全补齐的本次新增文件按受控恢复处理。不确定覆盖方向时，用单独的新目标生成新候选并核验，原有候选保留在隔离位置，任何将其改名的动作先核对绝对路径、目录身份及用户对保留位置的选择。绝不镜像清空、强制覆盖已有用户项目或自动清理整棵树。

## 4 · 原项目和 Git

回读同一项目 ID、主目录和其他源目录。文件校验通过后，为存在独立工作树的主仓运行：

```text
git_check.py repair NEW --baseline RUN/git-before.json --out RUN/git-repair.json
git_check.py verify NEW --baseline RUN/git-before.json --out RUN/git-after-switch.json
```

先确认独立工作树仍在原位置及指向确实属于这次原仓或已重连的目标。不要使用 prune、remove、reset 或强制检出。工作树状态摘要表达提交、分支、已跟踪/未跟踪条目的状态，文件内容保真由文件清单验证。外部工作树本次仍保持自己的物理工作副本。路径或改动状态出现差异时，区分用户的新工作和迁移错误，再决定如何接续，避免回写 C 盘旧索引覆盖 D 盘。

## 5 · 退出前给命令，重开后查真实状态

仅在实际换源且完成相关检查后，先问 A 手动改名或 B 由 PowerShell 改名。**要等退出 Codex 才能解除占用，因此在用户退出前生成并交付完整命令。** 初次准备时 OLD 仍为原实体，确保新旧根身份、备份名及此前校验仍吻合。

```text
cutover.py prepare --source OLD --target NEW --audit RUN --copy-audit RUN/tree-copy --mode manual
cutover.py prepare --source OLD --target NEW --audit RUN --copy-audit RUN/tree-copy --mode auto
```

这是两个互斥入口；**只执行选择的一行**。将助手生成的本项目 PowerShell 命令原样展示给用户，确保复制出来可以在 Windows PowerShell 5.1 或 PowerShell 7 运行。告诉用户把命令暂存记事本，完全退出 Codex 及托盘后台，再从 Windows 开始菜单打开独立 PowerShell（不要在项目内打开）。A 先把 OLD 手动改为指定 BACKUP，B 直接运行。两种方式都不需要修改代码。预期输出包括 FullName、LinkType=Junction、Target=NEW。

用户重开 Codex 并说“联接已建立”后运行 `cutover.py status --plan RUN/cutover-plan.json`。正确联接、正确目标、真实备份三者均核实后进入步骤 6。如果根已改名但联接未建，确认备份与原目录文件标识相同，使用本次计划的接续命令；如果旧名仍为实体或被别的东西占用、已有关联却指向别处、备份名冲突，说明准确路径与实际状态，停止该次切换，保留现状。不要在确认窗口打开时误报已保存，也不要用用户一句“已建立”代替现场核验。

## 6–7 · 读写验收与清理

仅在属于主目录的旧聊天中运行 `probe.py --plan RUN/cutover-plan.json --request-id 本次已登记UUID`，不指定 shell 工作目录。按 [聊天与桌面验收](chats.md) 执行用户选择的方式、核验回执并复读历史。

在备份仍是预期实体、联接仍指向 NEW 的前提下，最终运行 `tree_copy.py verify BACKUP NEW --audit RUN/backup-check`；有 Git 时另运行 `git_check.py verify NEW --baseline RUN/git-before.json --out RUN/git-final.json`。Git 输出选全新文件名，保留上一次结果。列出备份独有/目标独有、内容/流/硬链接/权限差异及变化发生时间。若差异只涉及探针所在根目录，或本次 Git 修复明确触及的反向指针文件的修改时间，应逐路径核对同字节 SHA-256、探针或 Git 回执、工作树注册位置与源稳定性，再单列为已解释的元数据变化。不要整体豁免 `.git`，其他差异一律单独判断。曾在 D 盘编辑时保留新版，C 盘存在独有或不能解释的数据时暂缓清理并举出具体差异。从不同 projectId 上读到的同名项目或未完成的旧聊天实际读写测试不能算通过。

向用户报告：聊天基准数、读取数、原组保留数、实际探针聊天；工作树数、关联位置和状态比对；备份可否清理、两条完整路径及审计位置。若用户指定了依赖旧绝对路径的图稿/程序，按需在新环境另做功能测试。审计材料不替代项目或聊天备份。如旧聊天测试未完成且属于待处理项，保留备份。已确认没有适用旧聊天时在最终报告写明该项不适用。清理备份由用户手动完成；进入原名联接删除内容会直接影响目标实体。

## 撤回或中断

换源前中断可以从原件继续使用；保留未通过验收的目标供核对。换源/修复 Git 后如需回退，先暂停两边写入、保存并比对新改动，核实备份身份和原项目 ID。按次序恢复实体原名、原项目配置和工作树关联，再验证文件/聊天/工作树；涉及已存在的联接或数据合并时先给出准确路径和操作影响，请用户确认。禁止对用户已有目录做递归删除。一次核验错误应保留原证据、定位失败阶段并尝试安全恢复，无须无故从头重做。
