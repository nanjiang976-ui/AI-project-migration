# 聊天、宿主项目和实际读写的验收

## 步骤 1 · 建立宿主基准

先区分正在执行迁移的助手和原聊天所属的宿主，再按[宿主适配](hosts.md)选择真正可用的入口。分别记录本次迁移编号、宿主/主机、项目根、可读的原生项目或会话 ID、迁移前 cwd、历史可读取的范围。没有稳定 ID 或枚举接口时如实标注；不能把迁移编号、目录名或另一次新会话当成原有会话身份。

**Codex**：读取原项目 ID、主目录和主机。多源项目记录完整列表和顺序，保留其他源。用 `list_threads` 对同一主机的未归档和归档 Codex 历史分别分页（`mode=history`、`source=codex`、`limit=50`，跟随 nextCursor），覆盖相关置顶聊天，按聊天 ID 去重。明确属于该 ID 的聊天，与只凭工作目录精确匹配所选来源或工作树的聊天分列。子目录聊天单独标注，用默认工作目录探针时，选择迁移前默认 cwd 精确匹配此来源的旧聊天。对基准 ID 使用 `read_thread`（通常 turnLimit=1、includeOutputs=false、maxOutputCharsPerItem=0）确认相同 ID 和真实历史回合，空聊天另记。

**Claude Code**：记录正式入口可取得的原会话 ID、项目路径和会话来源。恢复时使用同一个 ID，验证恢复后的身份；新开会话、fork 出来的 ID 或只读取了同名文件不算真实旧会话恢复。登录或模型调用可能产生额度消耗，先说明并取得许可。[Claude Code CLI](https://code.claude.com/docs/en/cli-reference)

**其他宿主**：请用户在原平台确认可见旧聊天和项目路径。有稳定标识则记录，在该宿主的原会话里验证。只有人工识别时，如实标明证明范围。没有批量历史接口就写“历史未能批量核验”；不要将空的查询结果解释为全项目没有旧聊天。

本机运行目录的 `chats-before.json` 仅保存元数据、覆盖范围和失败原因，不写入私人对话正文、凭据、命令输出或其他项目材料。

### Codex 多源与共享目录预检

1. 复制前从可用的正式入口读取「编辑项目」的完整源列表和原主次关系。项目简表可能只显示主要目录；取不到完整列表时，请用户核对并提供所有源路径及主要项。
2. 有多个源时，列出每条完整路径、主要或次要角色及已核实的引用项目，再问本次迁哪几条。其他源保留。按目录实际指向判断共享，同名目录先核对实体；只知道其他项目的主目录时，向用户确认尚未核实的引用关系。
3. 选中共享源时，列出引用它的项目及各自角色，说明共享目录只需搬一次，再确认这些项目是否一起换源。用户选择暂不协调时，这份共享目录原地保留。
4. 新迁移选中次要源（包括只选一个独享次要源）、多个实体或涉及多个引用项目时，先展示原目录和目标、受影响项目及角色、旧聊天验收方式。范围确认后进入 [Codex 批次](batch.md)。先接好旧入口，再换所选来源并回读原项目配置。只迁次要源时保留主目录，原聊天可从主目录启动附加源探针。[多源迁移 FAQ](https://github.com/nanjiang976-ui/AI-project-migration#faq)

## 步骤 4 · 确认新工作的位置（单目录流程）

Codex 在原项目的「编辑项目」添加已校验的目标完整路径。迁移主要目录时，把它的目标设为主要；接续已登记的单目录次要源迁移时，保留原主要目录。移除本次迁移的旧路径条目并保存，再核对项目 ID、完整源列表和主次角色。保留其他源及其相对顺序，核对信任提示中的完整路径。角色或源列表无法确认时，将换源标为待核验。CLI/通用宿主在实际目标打开新项目或新会话并验证默认 cwd，必要时给用户手动操作步骤。报告区分“设置已回读”“新会话已实测”“旧会话待验收”。不直接修改 SQLite、内部历史或会话文件。

## 步骤 6 · 链接验证以后才展示的两个选项（单目录流程）

提醒用户保留原名入口，再运行 `cutover.py status --plan RUN/cutover-plan.json` 确认 phase=linked。优先选迁移前即存在、默认工作目录为所选源、且当前空闲的原聊天。各源的会话与工作树聊天分别核对。接续已登记的单目录次要源迁移时，如果只有主目录旧聊天，可以记录该聊天对次要源的实际读取范围，双向读写仍待核验，备份继续保留。新迁移按上面的批次入口登记。

先登记用户选择、宿主/会话标识、请求 UUID、方式、计划和预期回执 `RUN/probe-<UUID>.json`，再给提示词或发送消息。同编号已发送时先检查回执和目标聊天，避免重新发送；超时不算通过。

**A．你手动发送。** 用户选具体旧聊天后，生成填好绝对脚本/运行路径、原会话标识和 UUID 的命令与提示词。用户在该宿主原聊天中执行并回报。收到“成功”后先核对预先登记的本机回执和可用的宿主记录，只追问仍不能核实的部分。

**B．助手自动验证。** 当前是基准中默认工作目录匹配所选源的旧聊天时直接自测。否则须有实际可用的跨会话能力，并在本次操作中让用户点名目标、明确同意“向这条原聊天发送一条可见的测试消息”。Codex 可用 `send_message_to_thread` 发送一次，再用 `wait_threads` 等待和 `read_thread` 核对；只有允许且可用时才使用。其他宿主没有该接口时由用户手动转交，不尝试从另一个平台模拟点击或无授权发送。

> 请在这条迁移前已存在的旧聊天中核对原会话身份，然后仅从其当前默认工作目录运行这次读写验收，不要 cd 或显式设置 shell 工具的 workdir。本次原路径是 [已核实的 OLD]，目标实体为 [已核实的 NEW]。请执行 [已填好脚本绝对路径、--plan、--request-id 及适用会话参数的命令]。请返回当前宿主会话标识/核验来源、实际默认目录、原名入口和目标实体读写状态、是否清理临时文件，以及本次 JSON 回执。身份或目录不符时说明现场并停止。

### 读取探针证据

- 在原路径形式的默认目录执行 `probe.py --plan PLAN --request-id UUID`。已用宿主证明恢复的是同一旧会话时，传入 `--resumed-session-id 原ID`（必须同时传请求 UUID），使解释器可接受已解析或已重绑到目标实体的默认目录，尤其是 macOS 的 getcwd 结果。对照原会话基准、宿主返回的恢复 ID、当前聊天和回执中的声明 ID。**填写参数只能传递声明，不能单靠该参数证明身份**。
- 文件部分先从默认目录独占创建随机文件，经旧名链接打开并写入，从真实目标读取、校验对象身份并追加，再从默认目录和旧入口读回。确认备份隔离，且只清理该测试文件。记录回执中的 cwd_form、source、target、UUID、原链接核实、双向读写与清理状态。
- 仅执行 `--filesystem-only` 时可以测试路径，但实际旧聊天写入数必须记为 **0**；它与 `--resumed-session-id` 互斥。新会话、其他聊天或人为切换到旧目录产生的回执，只能证明文件系统路径通畅。用这些证据不能将旧聊天测试标为 passed。
- 完整基准确证无适用旧聊天，步骤 6 可记 `not_applicable` 并报告零次实际旧聊天测试。缺授权、身份不可验证或宿主读写能力不足时，写明具体缺口。可以 waiting/blocked 等待补证；要继续汇报当前迁移成果时以 `unverified` 记录并保留备份。

## 步骤 7 · 聊天报告

重新读取可用历史并核对原 ID，分别列出基准数量、原归组保留数量、归档与未归档可读取数量、新增或丢失的对象。无此能力时说明已人工检查的内容和未验证覆盖。单列每条真正做过读写测试的原会话和请求编号、默认目录显示形式、实际目标、旧链接类型/指向及双向结果。文件迁移、路径兼容、会话恢复分别给结论。根据[执行手册](operations.md)和最新清理前比较，输出醒目的旧入口保留提示、目标实体与备份路径。

最终验收通过后，按下方的[验收聊天清理提醒](#temporary-acceptance-chats)收尾。

<a id="temporary-acceptance-chats"></a>

### 验收聊天清理提醒

整次迁移最终验收通过，并且验收证据已保存到本机运行记录或回执后，核对本次专门新建且仅用于验收的聊天。只列出后续无需用于补证的聊天，逐条写出实际标题，宿主提供聊天链接时附上链接，告诉用户可以自行手动删除这些聊天。原迁移聊天和迁移前已有的聊天继续保留。没有符合条件的聊天时省略此提醒。
